# My Bots control centre: implementation map and phased plan

## Actual surface and authority

My Bots is the Telegram `/mybots` / `/panel` interface in `agent/modules/clone/__init__.py`, not a browser application. This change upgrades that implementation; there is no new web mock, CSS framework or alternate database. Mobile layout means bounded native tables, short navigation rows and paginated lists; browser viewport tests would not prove Telegram rendering.

| Capability | Existing backend / UI | Gap and integration path |
|---|---|---|
| Saved identity, owner, channels, feature selection | `clone/store.py`, encrypted Clone records | Dashboard reads whitelisted fields; photo not fetched. Saved names/usernames are not a fresh Telegram verification. |

Dashboard lifecycle controls now use durable actor/revision/generation admission plus the existing reconciler. ## Ordered implementation slices

1. **Delivered phase one:** owner-private per-clone dashboard, configuration metadata, actual local command/plugin catalogue, diagnostic availability, working My Bots entry/navigation. No new mutating callback. No schema changes.
2. **Delivered for new dashboard actions:** durable owner/revision/generation admission for Start/Stop/Restart/Reconcile, confirmation, admission audit and reconciler integration. **Delivered follow-up for PostgreSQL:** legacy lifecycle buttons and `/delclone` route to fresh versioned confirmation; deletion uses durable owner/revision/generation admission. Local JSON compatibility and trusted internal provisioning/profile application/recovery calls retain their existing APIs.
3. Revision-aware configuration editor: preview/validate/save supported non-secret fields first; then individually audited secret/feature adapters. Use canonical writer, receipt identities and reconciler; persist no UI-only toggles.
4. Durable onboarding/checklist and contextual help from effective runtime manifests, credentials presence (never values) and verified group permissions; encrypted unfinished drafts with expiry/cleanup.
5. Owner-private diagnostic timeline, command search/categories and configuration controls where genuinely supported; paginated My Bots search/filter/recent-management views based on real data.

## Delivered slice and limits

The dedicated `cc:` dashboard routes authorize only the saved clone owner in that owner's private chat, reloading the canonical registry on every press. Unlike legacy controller-admin management paths, these new views do not grant the deployment Owner access to another owner's dashboard. Read-only views make no mutation. Confirmed dashboard lifecycle actions use `control_actions.py` and `CloneManager.control`; PostgreSQL legacy lifecycle buttons and `/delclone` now only browse a current confirmation, never execute an unversioned mutation. Profile-edit authorization and local JSON compatibility retain their existing policy.

The new `CloneManager.observe_worker` returns only whitelisted local registry/health facts, never a Clone serialization, token, key, session, raw error or provider configuration value. No worker is constructed for a stopped/unobserved clone just to manufacture command counts. Local absence is **not** fleet-wide offline status. Displayed enabled plugins include shell/mandatory modules; counts are explicitly registration counts, not group grants. Built-in navigation outside PluginRegistry is sourced from the running bot's own effective catalogue.

Unsupported items are text labelled Unavailable, not nonfunctional buttons: profile-photo fetching, per-worker CPU/RAM (workers share a process), event/log viewer, generic configuration reset, per-command toggles, durable onboarding resume and broader configuration-editor integration. No isolated-worker or full platform completion claim. Source licences and clone credit-free worker screens remain unchanged.

Validation evidence is recorded in `CODEBASE_AUDIT.md`. Test clients are synthetic; PostgreSQL transactions are real and disposable. No deployment or PR merge is authorized.


## Dashboard lifecycle admission (phase two)

On PostgreSQL-backed revision-tracked clones, dashboard Start/Stop/Restart/Reconcile buttons open a confirmation containing the expected desired revision and lifecycle generation. Confirmation reloads owner-private state and calls `CloneManager.control`. The backend refreshes start eligibility and serializes local application with existing start/recovery operations. `CloneControlActions.admit` locks the canonical registry and revision rows, verifies the **saved owner** (no controller-Owner bypass), compares revision/generation, advances the existing generation/tombstone sequence and commits lifecycle intent with a non-secret admission receipt. No configuration fields or snapshots are rewritten. No transaction spans Telegram/worker I/O, and no JSON lifecycle fallback is added.

Admission receipts live at scoped `clone_control:<bot_id>:<request_id>` document keys. They record action, actor, revision, generations and database time; **admitted is not completed**. Duplicate submission rejects and asks for refresh, rather than rerunning an unconfirmed operation. Receipts are retained as non-secret audit records across deletion/recreation, alongside existing lifecycle tombstone history; old callbacks cannot regain authority on recreation. A retention/compaction policy is not implemented here.

Start/restart/reconcile use strict assigned revision/generation and the existing lease-fenced reconciler. A newer stop, configuration update or deletion/recreation during application prevents acknowledgement and triggers local worker cleanup. Reconcile is potentially disruptive: advancing its lifecycle assignment can replace a local worker even at an unchanged configuration revision. Stop commits durable intent before local teardown and never claims synchronous fleet-wide shutdown. Remote controllers must observe and reconcile that intent. Existing cleanup error-reporting limitations remain; the UI says teardown **requested**, not externally proven complete.

The UI acknowledges validation before slow worker I/O and places the confirmed result on the refreshed card. Generic errors say the result is unconfirmed, never that no change occurred after a potentially committed admission. Database-unavailable and untracked local records get no new lifecycle buttons. Actual Telegram start/stop/clipboard/visual behavior remains unverified live.


## PostgreSQL legacy controls and fenced deletion (phase three)

Saved `clone:<id>:start|stop|restart|delete|delete_confirm` buttons now route only to a fresh `cc:` confirmation after the normal reload; even an old **Confirm delete** button cannot mutate directly. Extra payload segments reject rather than being ignored. The control centre independently requires the saved owner in that owner's private chat. `/delclone` also opens a versioned confirmation, refuses foreign/group/deployment-Owner substitution, and does not delete immediately. An untracked record cannot get an executable deletion confirmation. No fresh revision/generation is silently synthesized and executed on an old press.

`delete` extends the existing lifecycle-admission transaction: verify actor/revision/generation, advance the existing lifecycle tombstone, remove the canonical registry row and save a non-secret admission receipt atomically. Local teardown then uses the existing manager cleanup; remote controllers reconcile the missing record. Configuration writes and deletion serialize on the same registry/revision locks. New configurations or deletion/recreation invalidate saved deletion confirmations. The final card says **managed record removed**, not that all data or remote resources were synchronously destroyed.

Retention intentionally matches the previous managed-record deletion scope: encrypted revision/request history, non-secret lifecycle/audit history, clone-tenant data and previously delivered Telegram copies are not erased. A general privacy erasure/retention UI is not implemented. The existing local JSON compatibility behavior is unchanged; it is not a fallback for PostgreSQL failure. Internal creation, profile/configuration application and supervisor start/stop APIs are not converted into owner-interactive actions. The generic configuration editor and its legacy authorization policy remain a separate gate. No blanket claim that every possible call to a manager method now requires an interactive actor.

## Channel reset preview/save (phase four)

Configuration now offers **Clear log channel** / **Clear archive channel** only when a saved destination exists and revision metadata is available. Each action previews the current value, proposed unset value and operational consequences; Cancel returns without mutation. Confirm saves `{log_channel: null}` or `{storage_channel: null}` through the canonical encrypted revision writer and displays the saved desired revision. Existing copies are retained. No credentials, feature selection, mandatory moderation or approval/slot policy are modified. Saving does not itself claim worker application: pending desired configuration is applied by the existing reconciler/supervisor, and the UI offers the established dashboard route for explicit Reconcile. This is not an indefinite hold against automatic reconciliation.

Callbacks carry expected configuration revision and lifecycle generation. Private origin and exact saved owner are checked on every preview/save; the writer's new opt-in `owner_only` and `expected_generation` guards recheck those authorities under the registry transaction lock. Existing trusted writer callers keep their prior policy. Stale/replayed UI saves reject after canonical reload. DB outages have no local fallback. The preview warning is intentionally narrow: this is **not** a general editor, arbitrary channel entry, provider/channel permission verification, credential editor, command toggle or full configuration reset. Non-secret audit metadata continues to use canonical revision receipts; no competing writer or migration was introduced.

## Compact My Bots directory (phase five)

The existing controller panel now includes **Browse My Bots**; individual dashboard My Bots navigation opens `cc:list:all:0`. This read-only directory reloads canonical records on every press, restricts them to the exact requesting owner (no deployment-Owner override), sorts deterministically by bot ID and renders six entries per page. All / Start eligible / Stop intent filters operate on saved disabled intent, never inferred fleet-wide uptime. Each card states local worker observation separately and links directly to its dashboard. Refresh retains the filter and returns to its first page; Previous/Next retain the filter. Filter switches reset pagination. Stale pages reject explicitly rather than silently selecting another page. Empty states offer All or `/clone`; a controller-panel return preserves existing navigation.

Directory controls require the owner's private chat, use bounded callbacks and at most two buttons per row. Database failures do not render cached records. Dynamic bot names render through escaped native-table cells. No credentials, channel destinations, private provider configuration or raw errors enter this list. Search text, grid layout, recent-event sorting and live mobile/Telegram visual verification are not delivered by this phase. The legacy controller panel remains available with its existing button order for compatibility; this is a new compact browsing surface, not a rewrite of every existing list.

## Owner-scoped directory search (phase six)

`/mybots <name, @username or bot ID>` (also `/panel <query>`) now opens the compact directory filtered by case-insensitive substring of saved name/username/ID. No arguments retains the existing controller panel. Search is limited to 24 UTF-8 bytes without control characters; overlong input rejects explicitly without truncation. This limit leaves Telegram callback room for filter and page parameters, including Unicode queries. The saved-owner subset is selected before search; no provider/configuration/credential fields are searched. Private chat is mandatory.

Search is carried as canonical URL-safe base64 in bounded callback payloads, not as controller-local mutable session state or a database draft. This is **encoding, not encryption**: search only for non-secret bot identifiers; callback data is not a place for credentials. Search values are not added to logs or audit storage. Malformed/noncanonical UTF-8/base64 callbacks reject. Pagination, filters and refresh preserve the query; Clear search removes it. Filter switching/refresh starts at page one. Canonical records reload on every render, so remote changes/deletions affect results. No new persistence, mutation, schema or provider request is added. Grid/recent-event sorting and live mobile visual verification remain unfinished.

## Recent lifecycle admission activity (phase seven)

Each dashboard now links to **Recent activity**, a read-only paginated feed of existing `clone_control:<bot_id>:<request_id>` receipts. Six entries per page, newest receipt update first (document key tie-break), Previous/Next, Refresh and dashboard/directory return. Every entry is explicitly **admitted (not completion)**. Only allowlisted action, database admission time, expected revision and assigned generation are displayed. Unsupported/malformed receipts render an unavailable marker, never raw values. No actor/request IDs, errors, encrypted snapshots or credentials are displayed.

`activity.read_activity` checks current saved ownership under the same registry advisory transaction lock used by lifecycle/configuration writes before querying that bot's exact scoped receipt prefix. No wildcard scope matching, cross-owner controller-Owner override, JSON fallback or new writer. Callback private-origin checks remain mandatory. Deleted records cannot be browsed; retained bot-ID history becomes visible to the current saved owner after recreation and is explicitly labeled **retained across deletion/recreation**. It is not falsely presented as a new incarnation's worker activity. Empty and stale-page states are explicit. Database failure returns an error, not cached history.

Scope: lifecycle admission receipts only. Internal recovery, general controller events, configuration writes, completion/error logs and live Telegram actions are not captured by this feed. It adds no retention/compaction policy or generic logging system. Offset pagination can shift when newer receipts arrive; Refresh returns to the newest page. Large retained histories may need future indexed archival/storage work; every page query is bounded and timeout-limited, but no deep-history performance guarantee is claimed.

## Registry-backed command detail cards (phase eight)

Enabled commands on each Commands page now link to detail cards. Cards reload private saved-owner authority and re-observe that clone's current local registry, rejecting unknown/disabled commands or a missing inspectable worker rather than inferring availability from a saved profile. Only bounded Telegram command identifiers get detail callbacks. Each card displays the existing menu description, plugin, declared scope/permissions/dependencies, required credential **names** and capability names. No actual credential values, guessed provider readiness or invented argument examples.

A real Wzgram `CopyTextButton` copies the bare `/command`; it does not execute the command, include guessed arguments, or change its permissions. Back to Commands returns to page one. Existing dashboard/directory navigation remains; command links are at most two per row. A copied command is still subject to the clone's normal permissions, group approval and provider configuration. Detailed argument/schema-driven help, command search and per-command toggles remain unavailable. Local copy-button construction is tested; actual Telegram client clipboard behavior is not live-verified. Diagnostics now distinguishes the available lifecycle admission feed from still-unavailable raw worker logs.

## Command scope browsing (phase nine)

Commands now includes **All scopes / Private / Groups** controls built from the current clone's local registry. Private/Group views include plugins declared `all`; disabled-plugin commands remain excluded. Filter switches return to page one and Previous/Next retain the selected scope. The displayed declared-scope filter and count describe registry metadata, not per-caller execution authorization, provider readiness or group approval. Detail cards retain their independent current-registry checks; their Back button intentionally returns to the unfiltered first page. Existing `commands:<page>` links remain compatible. All new callbacks enforce saved-owner/private origin, allowlisted scopes and bounded page numbers. This is read-only and adds no storage or lifecycle changes. Free-text command search and plugin-category browsing remain future work.

## Clone-owned command guidance (phase ten)

The clone bot's own `/help command` and `worker:cmd:` cards now add declared tool context: friendly tool name, chat scope, permissions, dependencies, required credential names and capabilities from the selected shipped manifest. Mandatory moderation resolves to its actual underlying group-core manifest rather than guessing one combined permission set. Discovery still requires this worker's selected tools and current active commands before metadata is resolved. Built-in navigation states that no feature requirements are declared there instead of guessing scope/requirements. The existing actual command-copy action is unchanged.

Feature command cards now place **Get started** beside **Back to commands** (which retains the command's feature page). Guides recheck current availability. No controller credits, controller links, infrastructure identifiers, credential values or configuration snapshots are introduced into clone cards. Declared permissions are described as requirements, not a readiness check/access grant; optional group features still require Owner approval/admin activation and normal Telegram rights. Presentation only: no handler authorization, provider probing, feature activation or config storage changes. Detailed argument examples and dependency-health verification remain outside this change.

## Clone-owned paginated command search (phase eleven)

The worker's `/help <query>` substring results now paginate six matches per page instead of silently dropping all but the first six. Exact command/tool lookup still opens the existing detail/tool card first. Previous/Next encode the non-secret query in canonical URL-safe base64, and every callback re-evaluates the selected-tool/current active-command intersection. Stale pages reject; unselected tools cannot be surfaced by a forged query. Mandatory moderation remains discoverable where its commands are actually registered. No-match results explicitly explain the empty search instead of silently returning the overview. Fuzzy spelling suggestions are labeled and remain capped at six, distinct from exact substring pagination.

Search requires 1–24 UTF-8 bytes without control characters so callbacks remain within Telegram bounds; overlong free-text searches receive usage guidance rather than truncated results. Exact command names retain their direct lookup behavior. Query encoding is not encryption; use only command names, never secrets. No query database/session/log storage, new permissions, feature activation or provider calls. Worker search/cards remain free of controller credits. Going from results into a command card uses existing tool-page Back navigation, not a preserved search session. Live Telegram visuals remain unverified.

## Clone home quick actions and Availability navigation (phase twelve)

Worker Home now offers at most two actual copy-command buttons, drawn only from selected tools' current registered quick-start commands. Multi-tool homes prefer one first action per tool before taking a second action from one tool. Unknown/empty registry gets no shortcuts, unselected tools cannot contribute, and Help overview remains a browsing view without extra copy actions. A prominent line explains that copy does not execute and normal argument/access requirements still apply. This adds no handlers or auto-execution.

Availability now links directly to each currently registered selected workspace (including mandatory moderation when registered); unknown/unavailable tools get no executable workspace link. Refresh and Home/All tools stay present. Maximum two buttons per row and custom-emoji/plain-Unicode theme behavior retained. No controller credits, provider probes, configuration changes or online/readiness claims. These shortcuts are convenience navigation, not resumable onboarding or setup completion evidence; actual Telegram clipboard/visual behavior remains unverified.

## Clone help search relevance (phase thirteen)

Free-text worker help search now matches the existing menu descriptions as well as command names. Results rank command-name prefixes, then other name substrings, then description-only matches, with alphabetical ties and the same six-result pagination. Exact command/tool lookup still wins; fuzzy spelling suggestions are used only when neither names nor descriptions match. Case-folding precedes the query byte bound, keeping Unicode expansion from creating oversized callbacks. Selected-tool/current-registration filtering still precedes matching: optional tools and inactive commands cannot be discovered from their descriptions. Searches read static non-secret menu descriptions only, not provider data, tenant settings, credentials or message history. No AI/network search, mutations, execution or readiness inference. Existing live-visual/clipboard limitations remain.

## Music queue navigation polish (phase fourteen)

Music queue cards now use the current bot/clone theme for native reviewed icons, explicit styles and Unicode fallback. Previous/Next share a maximum-two-button navigation row; Refresh/Close share a separate row, with Close styled as danger. Callback payloads/actions are unchanged; Close only closes the card, not playback. The Music builder passes its own `ctx.theme`, preventing accidental presentation divergence between a clone and controller. Standalone QueueCards callers retain a default Theme for compatibility.

Read-only UI change: existing card token + chat + message + requesting-user checks, ten-minute expiry and bounded card retention are untouched. No voice engine/source/search/assistant implementation is enabled or altered. Real audible playback, Telegram visuals and queue-button delivery remain unverified live. Existing pending Music runtime/source/session changes are deliberately excluded; this is not a claim that remote URL/YouTube/search playback is ready. Broader Music engine/recovery/security work must be tested as separate complete slices.
