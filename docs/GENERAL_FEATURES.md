## Bounded current-group massban

Implemented main-bot `/massban ID ID …` (1–10 unique positive decimal IDs) in Operations and Help. Owner personal identity only; current group/supergroup only. Both caller and bot must hold current restrict/ban authority before each target. Current administrators, configured Owner and bot are protected. Metadata deadlines 5s, ban acknowledgement 10s; success only on explicit Telegram True. Stops on permission/config change or any unconfirmed effect; logs exception type only, reports confirmed/protected/unconfirmed counts and never retries automatically. Confirmed actions emit existing event-log records. No cross-chat mass banning, warning clearing, data deletion or provider calls.

Runtime serial admission and bounded 1,000-update-ID replay guard prevent concurrent/duplicate updates in one built handler. This is deliberately not durable exactly-once across restarts; an admitted invalid request also consumes its update ID. Bulk network effects cannot be transactional; partial effects remain and must be inspected before a new request. No global lock/database-lock claims.

Tests initially failed to import absent implementation, then cover exact current-chat effects, bounds/identity/private rejection before network, ambiguous failure redaction/no retry, protected admins, rights loss, Owner change and duplicate update admission. Full disposable-PG suite before final admission test: **2,078 passed, six existing missing-Music-dependency/preview failures in 22.66s**; massban targeted including final admission test **11 passed**. No full-green or live Telegram ban claim. No push/deployment; unrelated dirty changes preserved. Still missing: durable broadcast/copy cleanup, `/free`, social cards and translation.

## Bounded durable broadcast phase

Implemented main Operations `/broadcast -user` or `/broadcast -chat`, Owner personal identity and private chat only, replying to a forwardable message in that same chat. Up to 50 recipients from this bot's scoped cached users/chats documents. Rejects empty/oversized audience, missing/protected/service source, unsupported flags and missing DB. Uses Telegram forwards, not disguised copies. Fifteen-second forward deadline, stops at first ambiguous API/persistence error or changed Owner; no retries. No pinning, queued large campaigns, background-resume or automatic cleanup claim.

New additive scoped `agent_broadcasts` and `agent_broadcast_items` tables. Campaign+recipient admissions are one PG transaction, unique (tenant, private command message ID). Concurrent duplicate requests cannot both send. Every recipient is recorded before network effects; sending/forwarded/unconfirmed plus acknowledged destination ID persisted. Unknown/in-flight outcomes are never replayed; new command IDs intentionally constitute new campaigns. Source content is not stored in DB. Outcome saving can fail after Telegram accepts a forward; count says Telegram-confirmed, persistence explicitly unconfirmed. No exactly-once Telegram transaction claim. These records are the basis for future conservative duplicate cleanup, not authorization to delete arbitrary messages.

Tests use real disposable PG for concurrent unique admission, tenant separation and partial-delivery outcome/replay prevention, synthetic Telegram for calls and failures. Additional refusal tests cover unauthorized/group/pin/protected/DB-down no effects. Full suite before final four refusal cases **2,101 passed in 23.87s, no skips**. Final targeted run without DB **5 passed, 2 DB tests skipped**. No production schema calls or live Telegram sends. Changes remain local, not pushed/deployed. Remaining: broadcast pin mode and conservative recorded-duplicate cleanup, `/free` semantics, provider-backed translation.
